# VulnVeto engine — vendored copy

This directory contains a vendored copy of the **VulnVeto** security-scanning
engine, so AegisCode can be cloned, built, and run without a separate
VulnVeto repository checkout.

## What is vendored

- `src/` — the full engine source (TypeScript), including the four modules
  AegisCode's sidecar harness uses (`dep-scan`, `secret-scan`,
  `package-risk`, `sbom`) plus `ai/adapter` and `config`, which the harness
  also imports.
- `package.json`, `package-lock.json`, `tsconfig.json` — build metadata and
  the lockfile, so `npm ci` installs exactly the pinned dev dependencies.
- `README.md` — the engine's own documentation (describes the standalone
  CLI; AegisCode uses it as a library via the sidecar harness).
- `LICENSE`, `.gitignore` — preserved from upstream.

## What is NOT vendored (deliberately)

- `node_modules/` — installed by `npm ci` from the lockfile; never committed.
- `dist/` — build output, regenerated by `npm run build` (TypeScript
  compiler). Never committed.
- `.git/` — upstream version control metadata; the vendored copy is tracked
  by AegisCode's own git history instead.
- Caches, logs, reports, and secrets — none exist in the vendored tree.

## How AegisCode uses it

The C# security-scanning module
(`src/MeisterDev.ProPR.SecurityScanning/`) invokes the engine through the
Node sidecar harness `Resources/scan-harness.mjs`:

```
node Resources/scan-harness.mjs <engine-dir> <cloned-repo> <sbom-out>
```

`<engine-dir>` defaults to this directory (`tools/vulnveto`) resolved
relative to the AegisCode checkout — see
`SecurityScanningOptions.ResolveDefaultEngineDir()`. The override
`AEGIS_SECURITY_ENGINE_DIR` still exists for development and testing, but
a normal checkout does not need it.

The harness imports the **built** output: `dist/modules/*.js`,
`dist/ai/adapter.js`, `dist/config.js`. Building is therefore a required
setup step (see below).

## Build

```sh
# Linux / macOS
cd tools/vulnveto
npm ci
npm run build   # tsc → dist/
npm test        # build + node --test dist/tests/*.test.js
```

```powershell
# Windows PowerShell
cd tools\vulnveto
npm ci
npm run build
npm test
```

Or use the repository scripts, which do the same thing and verify the
expected runtime files exist:

```sh
scripts/build-vulnveto-engine.sh
```

```powershell
scripts\Build-VulnvetoEngine.ps1
```

Requires Node.js 20+ on PATH. No other runtime dependency: the engine
itself needs no npm packages at runtime. External tools it shells out to
are documented separately:

- **gitleaks** (secret scanning) — installed separately, never bundled.
  If it is missing, secret scanning is honestly reported as skipped and
  the scan is marked partial; it is never silently treated as clean.
  See `docs/SECURITY_ENGINE_INTEGRATION.md`.
- **git** (repository cloning) — performed by the C# module, not the engine.
- **OSV.dev API** (dependency advisories) — network access at scan time;
  without it, dependency findings are unavailable and the scan reports
  that honestly.

## Updating the vendored engine

To pull a newer upstream revision:

1. Clone or fetch the upstream repository separately (temporary directory).
2. Copy `src/`, `package.json`, `package-lock.json`, `tsconfig.json`,
   `README.md`, `LICENSE`, `.gitignore` over this directory.
3. Never copy `node_modules/`, `dist/`, or `.git/`.
4. Rebuild (`npm ci && npm run build`) and re-run the engine tests plus
   the AegisCode sidecar fixture checks (see
   `docs/VULNVETO_INTEGRATION_REPORT.md`).
5. Update the revision recorded at the top of this file and in
   `docs/VULNVETO_INTEGRATION_REPORT.md`.
6. Confirm the MIT `LICENSE` and attribution are still intact.

## What is bundled vs. separately installed

| Component | Bundled in AegisCode? | How it is obtained |

| VulnVeto engine source + build | Yes (`tools/vulnveto/`) | Vendored; built with `npm ci && npm run build` |
| Node.js 20+ | No | Developer installs from https://nodejs.org |
| gitleaks | No | Developer installs from https://github.com/gitleaks/gitleaks |
| git | No | Developer installs from https://git-scm.com |
| PostgreSQL (+ pgvector) | No | Developer installs / uses Neon (see setup docs) |
