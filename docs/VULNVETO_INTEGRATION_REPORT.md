# VulnVeto Integration Report — AegisCode is now self-contained

**Date:** 2026-10-24
**Branch:** `main` (commit `dd50600` at start; all changes below uncommitted, nothing pushed)
**Goal:** a developer can clone **AegisCode alone**, follow its setup docs,
build the bundled VulnVeto engine, configure the required external tools,
and run security scans — without cloning or building a separate VulnVeto
repository.

## 1. What was vendored

The VulnVeto security-scanning engine, copied into `tools/vulnveto/`:

| Vendored | Notes |
|---|---|
| `src/` (17 TypeScript files, 96 KB) | Full engine source, including the four modules the sidecar harness imports (`dep-scan`, `secret-scan`, `package-risk`, `sbom`) plus `ai/adapter` and `config` |
| `package.json`, `package-lock.json`, `tsconfig.json` | Build metadata + lockfile, so `npm ci` installs exactly the pinned dev dependencies |
| `README.md`, `LICENSE`, `.gitignore` | Preserved verbatim from upstream |
| `VENDORED_FROM.md` (new) | Origin, revision, license note, build/update instructions, bundled-vs-installed table |

**Deliberately NOT vendored:** `node_modules/` (26 MB, installed from the
lockfile), `dist/` (build output, regenerated by `tsc`, gitignored),
`.git/` (upstream version-control metadata), caches, logs, reports,
secrets. Nothing else was copied — no datasets, no unrelated files.

The separate original repository at `~/workspace/hackathon-domain2/vulnveto`
was **not modified** (read-only inspection only; its `dist/` was rebuilt by
an inspection subagent's test run, which is gitignored build output, not a
source change).

## 4. Runtime dependencies and external binaries

**Engine runtime dependencies: none.** VulnVeto's `package.json` declares
zero runtime dependencies; only dev dependencies (TypeScript `^5.9.3`,
`@types/node` `^26.6.5`), installed from the lockfile by `npm ci` (3
packages). Node.js 20+ is required (engine `engines` field; verified
against Node 24.22.1 on this VM).

| External tool | Required? | If missing | Source |
|---|---|---|---|
| Node.js 20+ | Yes (sidecar) | Scans fail closed with an install message | https://nodejs.org |
| git | Yes (cloning) | Clone fails with a user-safe error | https://git-scm.com |
| gitleaks | No (secret scan only) | `secret-scan` reported **skipped**, scan marked **partial** with the reason naming gitleaks — never silently clean; UI shows it under "Skipped" | https://github.com/gitleaks/gitleaks |
| OSV.dev API | No (advisories only) | `dep-scan` reports the fetch failure honestly in coverage | Network at scan time; `AEGIS_SECURITY_OSV_BASE_URL` override exists |

No executable binaries are committed to this repository. The application
never downloads or executes an unverified binary. `Dockerfile.deploy`
installs gitleaks from the official GitHub release tarball (pinned
`8.27.2`, Linux x64).

## 5. Commands to build and run on Windows

```powershell
# Prerequisites (verify first)
node --version     # must be 20+
dotnet --version   # must be 10.x
git --version
gitleaks version   # optional: enables secret scanning; see §4 if missing
# PostgreSQL 16 + pgvector (local install, or a Neon database)

# 1. Clone only AegisCode
git clone https://github.com/Prateek2007-cmd/aegiscode.git
cd aegiscode

# 2. Build the vendored engine (no separate VulnVeto clone)
scripts\Build-VulnvetoEngine.ps1
#   (or manually: cd tools\vulnveto; npm ci; npm run build; npm test; cd ..\..)

# 3. Configure the database (example: local PostgreSQL; use your own values)
#    Create the database and enable pgvector once:
#      createdb aegiscode-dev
#      psql -d aegiscode-dev -c "CREATE EXTENSION IF NOT EXISTS vector;"
#    Then set environment variables for this session (never commit them):
$env:DB_CONNECTION_STRING = "Host=localhost;Database=aegiscode-dev;Username=postgres;Password=<yours>"
$env:MEISTER_JWT_SECRET = "<32+ random characters>"
$env:MEISTER_BOOTSTRAP_ADMIN_USER = "admin"
$env:MEISTER_BOOTSTRAP_ADMIN_PASSWORD = "<yours>"
#    Optional, only if gitleaks is NOT on PATH:
#      $env:AEGIS_SECURITY_GITLEAKS_BINARY = "C:\path\to\gitleaks.exe"
#    NOTE: do NOT set AEGIS_SECURITY_ENGINE_DIR for a normal checkout —
#    the backend finds tools\vulnveto automatically.

# 4. Start the backend (API auto-applies EF Core migrations on startup;
#    it never drops or recreates an existing database)
$env:ASPNETCORE_URLS = "http://localhost:8080"
dotnet run --project src\MeisterDev.ProPR.Api

# 5. Start the frontend (second terminal)
cd frontend; npm install; npm run dev
#    Open http://localhost:5173, sign in as admin.

# 6. Run a sample security scan (after creating a client in the UI)
#    In the UI: open the client -> Security scans -> Start scan ->
#    repository https://github.com/Prateek2007-cmd/vulnveto
#    Or via API (replace CLIENT_ID and TOKEN):
#      Invoke-RestMethod -Method Post -Uri "http://localhost:8080/clients/<CLIENT_ID>/security-scans" `
#        -Headers @{ Authorization = "Bearer <TOKEN>" } -ContentType "application/json" `
#        -Body '{"repositoryUrl":"https://github.com/Prateek2007-cmd/vulnveto"}'

# Troubleshooting
#   "Scan engine not found"      -> re-run scripts\Build-VulnvetoEngine.ps1
#   "Node.js is not available"   -> install Node 20+ and restart PowerShell
#   "secret scanning skipped"    -> install gitleaks (see §4); the scan is
#                                   honestly partial, not clean
#   Port 8080 in use             -> $env:ASPNETCORE_URLS = "http://localhost:8081"
#   DB connection fails          -> check the connection string and that
#                                   PostgreSQL is running; never delete or
#                                   recreate a database to "fix" a connection
```

## 8. Whether a clean checkout works without a separate VulnVeto clone

**Yes — proven, not just documented.** The isolated-copy test (§7) built
the engine from a checkout copy with no external VulnVeto present, and the
database-backed API test proved the backend resolves that bundled engine
with no `AEGIS_SECURITY_ENGINE_DIR` set. The two remaining external
requirements are documented tools, not repositories: Node.js 20+, git, and
(optionally) gitleaks — plus PostgreSQL + pgvector for the API itself.

Windows path resolution could not be executed on this Linux VM; the
PowerShell script and the `Path.Combine`/`ArgumentList` handling are
written for Windows (no shell strings, no hardcoded separators), and the
spaces test on Linux covers the same class of bug. The PowerShell script
itself still needs one run on the laptop to be marked verified — see §10.

## 11. Security concerns discovered

None new. The integration preserves every guard the overnight audit
verified: URL allowlist + SSRF protection, safe clone flags
(`core.hooksPath=/dev/null`, `protocol.file.allow=never`, `--depth 1`,
`--no-tags`, `--no-recurse-submodules`), size/file caps, `ArgumentList`
process invocation (no shell), per-scan temp workdirs cleaned in
`finally`, redaction at the engine boundary re-verified before
persistence, client-scoped authorization on every endpoint, and
fail-closed partial states. The one behavior change to be aware of: a
checkout that has never built the engine now fails scans with a clear
"build the bundled engine" message instead of the old "set
`AEGIS_SECURITY_ENGINE_DIR`" message — fail-closed either way, but the
new message points at the fix instead of at an external checkout.
